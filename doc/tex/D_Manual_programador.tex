Los ficheros y directorios principales que se encuentran al nivel raíz del proyecto son:

\begin{itemize}
	\item \textbf{\texttt{webapp/}:} directorio raíz de la aplicación web.
	Contiene el punto de entrada de Flask, el código fuente, los recursos
	estáticos, las plantillas y los ficheros propios de ejecución de la
	aplicación.
	
	\item \textbf{\texttt{tests/}:} directorio que contiene la suite de
	pruebas automáticas del sistema. Incluye pruebas funcionales, de
	regresión, de integración y pruebas de navegador con Selenium.
	
	\item \textbf{\texttt{docker/}:} carpeta de soporte al despliegue. Incluye el script \texttt{entrypoint.sh}, encargado de preparar las carpetas necesarias y lanzar el comando final del contenedor, y el fichero \texttt{gunicorn.conf.py}, donde se define la configuración del servidor Gunicorn.
	
	\item \textbf{\texttt{instance/}:} directorio persistente de la aplicación. Contiene la base de datos SQLite, los modelos de inferencia, las colecciones, las imágenes subidas, las imágenes de perfil y los resultados generados. 
	
	\item \textbf{\texttt{Dockerfile}:} fichero que define la imagen Docker de la aplicación.
	
	\item \textbf{\texttt{docker-compose.yml}:} fichero de orquestación del
	despliegue. Define los servicios principales.
	
	\item \textbf{\texttt{.dockerignore}:} fichero utilizado para evitar que
	ciertos recursos entren dentro de la imagen Docker. Excluye entornos
	virtuales, cachés, informes de cobertura, datos persistentes, modelos,
	bases de datos y otros archivos generados.
	
	\item \textbf{\texttt{.env.example}:} plantilla de configuración de entorno.
	
	\item \textbf{\texttt{htmlcov/}:} informe HTML generado por
	\textit{coverage}. No forma parte del código fuente de la aplicación,
	sino que es un artefacto generado durante la validación.
	
	\item \textbf{\texttt{pytest.ini}:} fichero de configuración de
	\textit{pytest}. Define las rutas de búsqueda, el \textit{pythonpath}
	del proyecto y los marcadores específicos utilizados en la suite.
	
	\item \textbf{\texttt{.coveragerc}:} fichero de configuración de
	\textit{coverage}, utilizado para medir la cobertura sobre el paquete
	principal de la aplicación.
\end{itemize}

Dentro de \texttt{webapp/} se encuentran los ficheros propios de la
aplicación, entre los que destacan:

\begin{itemize}
	\item \textbf{\texttt{run.py}:} punto de entrada de la aplicación Flask.
	
	\item \textbf{\texttt{requirements.txt}:} listado principal de
	dependencias necesarias para instalar y ejecutar la aplicación.
	
	\item \textbf{\texttt{requirements.freeze.txt}:} listado congelado de
	dependencias del entorno, útil para reproducir instalaciones concretas.
	
	\item \textbf{\texttt{requirements-selenium.txt}:} dependencias

	\item \textbf{\texttt{babel.cfg}:} configuración utilizada por
	Flask-Babel para localizar y extraer textos traducibles.
	
	\item \textbf{\texttt{messages.pot}:} plantilla base de traducciones
	generada a partir de los textos extraídos.
	
	\item \textbf{\texttt{trazasytrazadas/}:} paquete principal de código
	fuente de la aplicación. Contiene la factoría de aplicación, los

Esta decisión evita que los modelos queden embebidos dentro de la imagen y permite actualizarlos o sustituirlos sin reconstruir toda la aplicación.

\section{Manual del programador} 

El objetivo de este apartado es proporcionar una visión técnica del funcionamiento interno de la aplicación, de forma que un futuro desarrollador pueda comprender su estructura, mantenerla y ampliarla sin necesidad de reconstruir todo el razonamiento realizado durante el desarrollo. 

\subsection{Inferencia: \textit{pickle}, PyTorch y modelos por \textit{fold}} 

La aplicación trabaja con modelos de segmentación semántica procedentes del trabajo base sobre detección de trazas de herbivoría~\cite{diezpastora2025trails}. Durante el desarrollo se analizaron dos rutas principales para integrar dichos modelos en la aplicación web, como ya se comentó en el apartado de \textit{Aspectos relevantes del desarrollo del proyecto} de la memoria.

Esta decisión no se tomó únicamente por rendimiento, sino principalmente por fidelidad respecto al comportamiento del \textit{pipeline} original. El objetivo era conservar la mayor coherencia posible con los resultados esperados del modelo base, evitando introducir variaciones en la segmentación derivadas del cambio de formato de despliegue. No obstante, esta elección tiene implicaciones importantes para futuros desarrolladores.

Los ficheros \texttt{pickle} deben tratarse como artefactos sensibles y cargarse únicamente desde ubicaciones controladas por la aplicación. No deben aceptarse modelos arbitrarios procedentes de usuarios sin permisos de administración, ya que la carga de este tipo de ficheros puede ejecutar estructuras internas no deseadas si no se controla adecuadamente el origen. Por ello, cualquier funcionalidad relacionada con subida, validación o activación de modelos debe mantenerse restringida al panel de administración. 

También debe tenerse en cuenta que cualquier cambio en el formato del modelo exige repetir las pruebas de equivalencia de inferencia. Si se sustituye \texttt{pickle} por TorchScript, \texttt{safetensors} u otro formato, no basta con comprobar que el modelo carga correctamente: es necesario comparar las máscaras generadas y verificar que las diferencias no afectan al resultado funcional. Del mismo modo, actualizaciones de PyTorch, \texttt{segmentation-models-pytorch}, \texttt{timm} u otras dependencias relacionadas con la inferencia pueden modificar el comportamiento del modelo y deben validarse cuidadosamente. 

Finalmente, un programador que modifique esta parte debe prestar especial atención al preprocesado de la imagen. Cambios en la normalización, el tamaño de entrada, el orden de canales, el umbral de binarización o el postprocesado de la máscara pueden alterar las trazas detectadas, incluso cuando el modelo utilizado sea el mismo. Por ello, cualquier cambio en la inferencia debe acompañarse de pruebas con imágenes representativas y resultados esperados.

\subsubsection{Compatibilidad de PyTorch con GPU en despliegue}

Además de la compatibilidad funcional del modelo, debe revisarse la compatibilidad entre PyTorch, CUDA y el hardware disponible en el entorno de despliegue. El entorno local o general del proyecto puede mantener las versiones fijadas en \texttt{requirements.txt}, pero el \texttt{Dockerfile} de producción puede requerir una \textit{build} específica de PyTorch para ajustarse a las GPU del servidor. En el servidor Gamma se detectaron GPU NVIDIA TITAN Xp, cuya capacidad CUDA es \texttt{sm\_61}. La \textit{build} inicial \texttt{torch 2.10.0+cu128} no resultaba adecuada, ya que soportaba arquitecturas a partir de \texttt{sm\_70}; por ello, se sustituyó en el contenedor de despliegue por \texttt{torch 2.7.1+cu118} y \texttt{torchvision 0.22.1+cu118}.

Un futuro desarrollador no debería actualizar las versiones de PyTorch o CUDA sin repetir pruebas reales de inferencia. No basta con comprobar que \texttt{torch.cuda.is\_available()} devuelve \texttt{True}, especialmente si PyTorch muestra advertencias de arquitectura. Debe verificarse también el número de dispositivos mediante \texttt{torch.cuda.device\_count()}, revisar el estado del sistema con \texttt{nvidia-smi} y ejecutar al menos una operación real en GPU antes de considerar válido el entorno. Del mismo modo, cualquier cambio de versión debe probar la carga del modelo activo y una inferencia completa sobre una imagen representativa, ya que la compatibilidad del \textit{runtime} forma parte de la reproducibilidad del sistema.

\subsection{Worker asíncrono de procesamiento de trazas} 

Uno de los componentes más relevantes del sistema es el \textit{worker} asíncrono de procesamiento de trazas, implementado en torno a \texttt{trace\_worker.py}. Su función es procesar las teselas pendientes de las colecciones geoespaciales sin bloquear la petición HTTP del usuario. De este modo, cuando el usuario genera una zona desde el visor cartográfico, la aplicación puede responder de forma rápida registrando la colección y dejando el cálculo de trazas para un procesamiento posterior en segundo plano.

En este flujo, la entidad \texttt{Parcela} representa una colección generada desde el visor, mientras que cada registro de \texttt{Foto} representa una tesela concreta dentro de dicha colección. Cada tesela puede encontrarse en distintos estados de procesamiento, principalmente \texttt{pending}, \texttt{processing}, \texttt{completed} o \texttt{failed}. La base de datos SQLite actúa así como una cola persistente de trabajo, almacenando qué imágenes están pendientes, cuáles están siendo procesadas, cuáles han terminado correctamente y cuáles han fallado. Esta decisión permite que el estado del procesamiento sobreviva entre peticiones y que la interfaz pueda consultar el avance de la colección sin depender de una tarea HTTP de larga duración.

El flujo general comienza cuando el usuario define una zona en el visor cartográfico. En ese momento, la aplicación crea la parcela o colección y registra sus teselas asociadas como fotos pendientes de procesamiento. Posteriormente, uno o varios \textit{workers} reclaman progresivamente esas teselas, las marcan como \texttt{processing}, ejecutan la inferencia, guardan los resultados y actualizan su estado final a \texttt{completed} o \texttt{failed}. Esta arquitectura permite procesamiento concurrente controlado, manteniendo al mismo tiempo trazabilidad sobre cada tesela y sobre el estado global de la colección.

Para evitar que dos \textit{workers} procesen simultáneamente la misma tesela, la reclamación de trabajo se realiza de forma atómica. La función de \textit{claim} abre una transacción corta en SQLite mediante \texttt{BEGIN IMMEDIATE}, selecciona candidatas que no pertenezcan a parcelas pausadas y que se encuentren en estado \texttt{pending} o en \texttt{processing} antiguo, y actualiza condicionalmente su estado a \texttt{processing}. En esa misma operación se incrementa el campo \texttt{numero\_intentos} y se confirma la transacción inmediatamente. La inferencia se ejecuta después, fuera de la transacción, para no mantener bloqueada la base de datos durante operaciones costosas como la carga de imagen, el cálculo con PyTorch o la escritura de resultados.

Este diseño es importante porque combina concurrencia y consistencia. Por un lado, permite ejecutar varios \textit{workers} en paralelo, cuyo número puede configurarse desde el fichero \texttt{.env}. Por otro lado, evita que una misma tesela sea reclamada dos veces y reduce el tiempo durante el cual SQLite permanece bloqueado. La base de datos se utiliza únicamente para coordinar estados y asignar trabajo, mientras que el procesamiento pesado se realiza fuera de la transacción. De esta forma, el sistema mantiene una cola persistente sencilla, pero suficientemente robusta para el flujo de colecciones implementado.

También se contempla la recuperación de teselas bloqueadas en estado \texttt{processing}. Si un \textit{worker} se detiene de forma inesperada, una foto podría quedar marcada como en procesamiento sin llegar a finalizar. Para evitar que quede indefinidamente en ese estado, el sistema utiliza el parámetro \texttt{TRACE\_WORKER\_STALE\_SECONDS}, que permite considerar antigua una tesela en \texttt{processing} y volver a reclamarla. Este valor no debe configurarse demasiado bajo, ya que una inferencia lenta podría interpretarse erróneamente como bloqueada y provocar reintentos innecesarios.

La pausa y reanudación del procesamiento se gestiona mediante el estado global de la colección. La pausa se representa con \texttt{Parcela.estado = "paused"}, sin añadir una columna adicional específica para esta operación. Cuando una colección se pausa, los \textit{workers} no deben reclamar nuevas teselas asociadas a ella y, si procede, las fotos que estuvieran en \texttt{processing} pueden volver a \texttt{pending} para ser retomadas posteriormente. Esta pausa afecta únicamente a la parcela o colección seleccionada, no al sistema completo, por lo que no deben detenerse hilos globales ni bloquearse todos los procesos de la aplicación.

Finalmente, el \textit{worker} debe revalidar el estado de la parcela antes de guardar un resultado. Si una tesela termina su procesamiento mientras la colección ha sido pausada, el resultado no debe marcarse indebidamente como completado dentro de un flujo ya detenido por el usuario. Del mismo modo, una colección ya completada no debe poder pausarse, ya que no existe trabajo pendiente que interrumpir. Estos invariantes son importantes para mantener la coherencia entre la interfaz, la base de datos y los resultados generados en el sistema de ficheros.

\subsection{Worker asíncrono de validación de modelos}

El segundo proceso asíncrono relevante está asociado a la validación de modelos subidos desde el panel de administración. Cuando un administrador incorpora un nuevo modelo, el sistema no debe asumir automáticamente que dicho artefacto es válido ni bloquear la interfaz hasta completar todas las comprobaciones. Por ello, el modelo puede registrarse inicialmente como pendiente y validarse en segundo plano.

El flujo general consiste en que el administrador sube un fichero de modelo, el sistema lo registra como pendiente y se lanza una tarea de validación. Si la comprobación finaliza correctamente, el modelo pasa a estado validado y queda disponible para su posible activación. En caso contrario, el modelo no debe quedar disponible para inferencia y debe eliminarse. La interfaz de administración debe informar al usuario administrador del resultado cuando proceda. 

Por tanto, no basta con comprobar que el fichero existe: debe verificarse que el modelo puede cargarse, que admite una entrada compatible, que produce una salida válida y que no genera errores durante una inferencia básica. Cualquier modificación de esta parte debe probar, como mínimo, la subida de modelos, el estado pendiente, la validación correcta, la validación fallida, la activación posterior, la ausencia de bloqueo de la interfaz y la restricción de permisos a usuarios administradores. 

\subsection{Gestión de modelos desde administración}

La aplicación incorpora una sección de administración de modelos que permite al administrador consultar los modelos disponibles, subir nuevos artefactos, renombrarlos, comprobar su estado, activarlos y revisar su fecha de creación. Esta funcionalidad tiene como objetivo evitar que el sistema quede ligado de forma rígida a un único modelo de segmentación, facilitando su evolución a medida que existan nuevas versiones o modelos.

La regla de negocio actual establece que solo debe existir un modelo activo para inferencia. Si en el futuro se decide permitir varios modelos activos, modelos por usuario o selección manual en cada ejecución, será necesario revisar de forma coordinada la lógica de \texttt{model\_store.py}, las rutas de administración, el componente de inferencia y los tests asociados.

También debe mantenerse la trazabilidad entre modelos e imágenes procesadas. Cuando una foto se procesa con un modelo concreto, conviene conservar la referencia al modelo utilizado, de forma que posteriormente pueda conocerse qué versión generó las trazas.

\subsection{Seguridad y permisos}

La seguridad del sistema depende en gran medida de mantener una separación clara entre usuarios normales y administradores. Las rutas de administración deben requerir siempre rol de administrador, y los usuarios sin dichos permisos no deben poder acceder a la gestión de usuarios ni a la gestión de modelos. Esta restricción debe aplicarse tanto en la interfaz como en las rutas del servidor, ya que ocultar botones en el frontend no es suficiente para proteger una operación sensible. 

Las colecciones, imágenes y resultados deben comprobar siempre la propiedad o los permisos antes de mostrarse o descargarse. Un usuario normal solo debería acceder a sus propios recursos, salvo que se defina explícitamente otro comportamiento. Del mismo modo, las imágenes de perfil deben tratarse como datos personales y gestionarse con cuidado, evitando exponer rutas internas o permitir acceso directo a ficheros privados sin validación. 

Los modelos subidos al sistema son ficheros especialmente sensibles. En particular, los modelos serializados mediante \texttt{pickle} no deben cargarse desde fuentes no controladas ni desde usuarios sin privilegios. La carga de modelos debe considerarse una operación de confianza restringida a administradores. Además, no deben exponerse rutas directas a modelos, imágenes subidas, bases de datos, resultados JSON o ficheros internos sin pasar por los mecanismos de autorización de la aplicación.

\subsection{Ejecución separada de web y \textit{worker} en Docker}

En el despliegue contenedorizado se separa la ejecución de la aplicación web y del procesamiento de trazas en servicios distintos. El servicio \texttt{web} ejecuta la aplicación Flask mediante Gunicorn y atiende las peticiones HTTP del navegador. Por su parte, el servicio \texttt{worker} ejecuta explícitamente el proceso de trazas mediante el comando \texttt{flask --app run:app traces-worker}, sin publicar puertos ni atender tráfico web. Esta separación permite que la interfaz y el procesamiento en segundo plano evolucionen de forma independiente, manteniendo responsabilidades claras dentro del despliegue.

Para evitar duplicidades, el servicio \texttt{web} debe tener desactivado el arranque automático del \textit{worker}, configurando \texttt{AUTO\_START\_TRACE\_WORKER=false}. El procesamiento debe iniciarse únicamente desde el servicio \texttt{worker} definido en Docker. Ambos contenedores deben montar los mismos volúmenes de datos, de forma que compartan la base de datos SQLite, las imágenes, las teselas, los resultados JSON y los modelos almacenados en el sistema de ficheros. En este esquema, los modelos no deben copiarse dentro de la imagen Docker, sino mantenerse en volúmenes externos, facilitando su actualización y evitando reconstrucciones innecesarias de la imagen.

La arquitectura permite escalar el procesamiento lanzando varios contenedores de tipo \texttt{worker}. Por ejemplo, puede aumentarse el número de procesos de trazas mediante el siguiente comando:

\begin{pythonbox}{Ejecución de contenedores con Docker Compose}
docker compose up -d --scale worker=2
\end{pythonbox}

La concurrencia total del sistema viene determinada por el número de contenedores \texttt{worker} multiplicado por el valor de \texttt{TRACE\_WORKER\_CONCURRENCY}. Por tanto, si se ejecutan dos contenedores \texttt{worker} y cada uno tiene una concurrencia interna de dos, el sistema podrá procesar hasta cuatro tareas de forma concurrente, siempre dentro de los límites impuestos por la base de datos, la GPU y el sistema de ficheros.

Un futuro desarrollador debe tener especial cuidado al modificar estos parámetros. No conviene aumentar \texttt{WEB\_CONCURRENCY} sin revisar previamente el comportamiento de SQLite, ya que incrementar el número de procesos web puede aumentar la presión sobre la base de datos. Tampoco debe mezclarse el arranque automático del \textit{worker} dentro del servicio \texttt{web} con un servicio \texttt{worker} independiente, porque se crearían procesos duplicados y sería más difícil razonar sobre la concurrencia real. La separación recomendada es mantener \texttt{web} para HTTP y \texttt{worker} para procesamiento de trazas.

\subsection{Recomendaciones de mantenimiento}

Para mantener la aplicación de forma segura y sostenible, se recomienda no reescribir la arquitectura sin una necesidad clara. La estructura actual basada en Flask, \textit{Application Factory}, \textit{blueprints}, plantillas Jinja y módulos separados por responsabilidad permite evolucionar el sistema de forma incremental sin introducir una complejidad excesiva. 

Antes de modificar la inferencia, se deberían preparar pruebas con imágenes representativas y máscaras esperadas, prestando atención a posibles cambios en bordes, trazas finas y regiones de baja visibilidad. Antes de modificar los \textit{workers}, conviene comprobar todos los estados relevantes: pendiente, en procesamiento, pausado, completado y fallido. Del mismo modo, cualquier cambio en la gestión de modelos debe validar subida, fallo de validación, validación correcta, activación y permisos de administración. 

En la parte de interfaz, los cambios en JavaScript deben revisar que no se rompe la inyección de configuración desde Jinja. La aplicación utiliza objetos globales para pasar URLs, textos traducidos y datos iniciales a los scripts del navegador, por lo que cualquier modificación debe respetar ese contrato entre servidor y cliente. Asimismo, cuando se añadan nuevos textos visibles, deben actualizarse las traducciones correspondientes. 

Finalmente, es importante mantener actualizados los tests de \texttt{pytest} y Selenium conforme evolucione la aplicación. También debe prestarse especial atención a las actualizaciones de PyTorch, \texttt{segmentation-models-pytorch}, \texttt{timm} y bibliotecas relacionadas con modelos, ya que pequeñas variaciones de versión pueden afectar a la carga, validación o salida de inferencia.

\section{Compilación, instalación y ejecución del proyecto}

En este apartado se describen los pasos necesarios para preparar el entorno de desarrollo, instalar las dependencias y ejecutar la aplicación. Al tratarse de un proyecto desarrollado con Python y Flask, no existe una fase de compilación clásica como ocurre en lenguajes compilados. En este caso, la preparación consiste en crear un entorno virtual, instalar las dependencias, preparar los recursos locales de la aplicación, compilar los catálogos de traducción si procede y arrancar el servidor web.

\subsection{Requisitos previos}

Para poder instalar y ejecutar correctamente el proyecto es necesario disponer de una serie de herramientas básicas en el equipo de desarrollo. En primer lugar, se requiere una versión de Python 3 compatible con el proyecto, junto con \texttt{pip} para la instalación de dependencias. También es necesario contar con Git para obtener el código fuente desde el repositorio y con un navegador web para acceder a la aplicación una vez iniciada.

Además, se recomienda trabajar siempre dentro de un entorno virtual de Python, de forma que las dependencias del proyecto queden aisladas del resto del sistema. El proyecto puede ejecutarse tanto en Windows como en sistemas Linux o macOS, aunque para un despliegue en servidor se recomienda un entorno Linux con Gunicorn como servidor WSGI.

De forma complementaria, el proyecto incluye pruebas de navegador basadas en Selenium. No obstante, la instalación y ejecución de dichas pruebas se documenta en el apartado específico de pruebas del sistema.

\subsection{Obtención del proyecto}

El primer paso consiste en clonar o descargar el repositorio completo del Trabajo de Fin de Grado. Una vez obtenido, se debe acceder a la raíz del proyecto, desde donde se realizarán las tareas generales de instalación y prueba.

\begin{gitbox}{Obtención del proyecto}

cd TFG-Marcos-Zamorano
\end{gitbox}

En caso de recibir el proyecto como un archivo comprimido, bastará con descomprimirlo y situarse en la carpeta raíz equivalente.

\subsection{Creación del entorno virtual}

Para evitar conflictos con otras instalaciones de Python, se debe crear un entorno virtual específico para el proyecto. En Windows, utilizando PowerShell, puede hacerse mediante los siguientes comandos:

\subsection{Internacionalización}

La aplicación utiliza Flask-Babel y catálogos \texttt{gettext} para gestionar la internacionalización de los textos visibles. Cuando se modifican textos traducibles en las plantillas o en el código Python, el flujo habitual consiste en extraer los mensajes, actualizar los catálogos de traducción y compilar los ficheros finales.

Desde el directorio \texttt{webapp}, el proceso es el siguiente:

\begin{pythonbox}{Internacionalización}
cd webapp
pybabel extract -F babel.cfg -o messages.pot .
pybabel update -i messages.pot -d trazasytrazadas/translations
pybabel compile -d trazasytrazadas/translations
\end{pythonbox}

Si únicamente se desea ejecutar la aplicación y los catálogos ya se encuentran actualizados, puede bastar con recompilar las traducciones:

\begin{pythonbox}{Compilación de traducciones}
cd webapp
pybabel compile -d trazasytrazadas/translations
\end{pythonbox}

Los textos traducibles deben envolverse mediante \texttt{\_()} en las plantillas o en el código Python. En el caso de los textos utilizados por JavaScript, no se debe insertar Jinja directamente dentro de ficheros \texttt{.js}. En su lugar, la aplicación inyecta desde las plantillas objetos globales con las cadenas ya traducidas y la configuración necesaria para cada vista.

\begin{pythonbox}{Ejecución local de la aplicación}

python run.py
\end{pythonbox}

Tras iniciar el servidor, la aplicación estará disponible en la siguiente dirección:

\begin{infocmdbox}{Dirección local de la aplicación}	http://127.0.0.1:5000
\end{infocmdbox}

Desde esta URL se puede acceder a la interfaz principal de la aplicación, cargar imágenes, iniciar sesión, utilizar el visor cartográfico y acceder al resto de funcionalidades disponibles según el rol del usuario.

\subsection{Ejecución en modo desarrollo}

Durante la fase de desarrollo puede resultar útil ejecutar Flask en modo depuración, ya que permite recargar automáticamente el servidor ante cambios en el código y mostrar información detallada de errores. Para ello puede utilizarse el siguiente comando:

\begin{pythonbox}{Ejecución en modo desarrollo}
flask --app run --debug run
\end{pythonbox}

Este modo debe utilizarse únicamente en entornos locales de desarrollo. No debe activarse en un servidor de producción ni en el de la Universidad de Burgos, ya que puede exponer información interna de la aplicación y comprometer su seguridad.

\subsection{Ejecución en servidor con Gunicorn}

Durante el desarrollo local la aplicación puede ejecutarse mediante el servidor integrado de Flask, ya que resulta suficiente para depuración y pruebas rápidas. Sin embargo, en un entorno de producción no debe utilizarse dicho servidor ni activarse el modo \textit{debug}. Para el despliegue se emplea Gunicorn, que actúa como servidor WSGI entre la aplicación Flask y la infraestructura del servidor. El punto de entrada de la aplicación es \texttt{run:app}, y la configuración específica del despliegue se encuentra en el fichero \texttt{docker/gunicorn.conf.py}.

Conceptualmente, la aplicación podría arrancarse con el siguiente comando:

\begin{dockerbox}{Arranque conceptual de Gunicorn}
	gunicorn --config /app/docker/gunicorn.conf.py run:app
\end{dockerbox}

No obstante, en el despliegue normal este comando no se ejecuta manualmente, sino que lo lanza el contenedor \texttt{web} definido en Docker Compose. Este servicio se encarga de atender las peticiones HTTP de la aplicación, pero no debe procesar directamente colecciones pesadas. Para mantener un comportamiento estable con SQLite, se conserva \texttt{WEB\_CONCURRENCY=1}, mientras que la concurrencia HTTP ligera se gestiona mediante \textit{threads} configurados en Gunicorn.

\subsection{Despliegue con Docker Compose}

El despliegue con Docker Compose permite levantar la aplicación de forma reproducible, separando el servicio web del servicio encargado del procesamiento de trazas. El primer paso consiste en copiar la carpeta completa del proyecto al servidor o entregarla al evaluador. La estructura esperada en la raíz del proyecto debe incluir, al menos, los siguientes elementos:

\begin{infocmdbox}{Estructura mínima esperada en la raíz del proyecto}
Dockerfile
docker-compose.yml
.env.example
docker/
webapp/
instance/
\end{infocmdbox}

A continuación, debe crearse el fichero de variables de entorno a partir de la plantilla proporcionada:

\begin{dockerbox}{Creación del fichero de variables de entorno}
cp .env.example .env
\end{dockerbox}

También debe generarse una clave secreta para la aplicación:

\begin{pythonbox}{Generación de clave secreta}
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
\end{pythonbox}

El valor generado debe copiarse en la variable correspondiente del fichero \texttt{.env}:

\begin{infocmdbox}{Variable de clave secreta}
SECRET_KEY=...
\end{infocmdbox}

Antes de arrancar los servicios debe comprobarse la existencia del directorio \texttt{instance}. Si se desea partir de un entorno vacío, puede crearse mediante:

\begin{dockerbox}{Creación del directorio de instancia}
mkdir -p instance
\end{dockerbox}

Si se entrega un directorio \texttt{instance} ya preparado con datos de demostración, modelos y recursos asociados, no debe sobrescribirse, ya que contiene la base de datos y los ficheros persistentes necesarios para la ejecución.

Una vez preparada la configuración, los servicios se levantan desde la raíz del proyecto con:

\begin{dockerbox}{Construcción y arranque de servicios}
docker compose up -d --build
\end{dockerbox}

El estado de los contenedores puede comprobarse mediante:

\begin{dockerbox}{Comprobación del estado de contenedores}

\end{dockerbox}

Para revisar los registros de ejecución, pueden consultarse los logs del servicio web y del servicio de procesamiento:

\begin{dockerbox}{Consulta de logs de los servicios}
docker compose logs -f web
docker compose logs -f worker
\end{dockerbox}

En un despliegue local, la aplicación queda accesible normalmente en:

\begin{infocmdbox}{Dirección de acceso en despliegue local}
http://localhost:8000
\end{infocmdbox}

En el servidor Gamma, la dirección de acceso utilizada es:

\begin{infocmdbox}{Dirección de acceso en el servidor Gamma}
http://10.168.168.34:8000
\end{infocmdbox}

El acceso externo dependerá de la red de la universidad, de la disponibilidad del servidor y de que los contenedores estén correctamente levantados.

\subsection{Preparación de datos persistentes}

El directorio \texttt{instance} contiene los datos persistentes de la aplicación. Este directorio no debe formar parte de la imagen Docker, sino montarse como volumen para que la información sobreviva a reconstrucciones de la imagen o reinicios de los contenedores. La estructura esperada es la siguiente:

\begin{infocmdbox}{Estructura esperada del directorio de instancia}
instance/
|-- trazasytrazadas.sqlite
|-- model/
|   |-- fold.0
|   |-- fold.1
|   `-- fold.2
|-- collection/
|-- profile_images/
|-- uploads/
`-- outputs/
\end{infocmdbox}

La base de datos \texttt{trazasytrazadas.sqlite} almacena usuarios, modelos registrados, colecciones, teselas y estados de procesamiento. Los modelos reales deben situarse en \texttt{instance/model}, las colecciones y resultados generados se almacenan en \texttt{instance/collection}, las imágenes de perfil en \texttt{instance/profile\_images} y los ficheros asociados a subidas y salidas en \texttt{uploads} y \texttt{outputs}. Para la evaluación del proyecto puede entregarse un directorio \texttt{instance} de demostración ya preparado, evitando que el tribunal tenga que generar usuarios, modelos o colecciones desde cero.

Antes de realizar copias de seguridad es recomendable detener los servicios, especialmente para evitar copiar la base de datos SQLite mientras está siendo escrita:

\begin{dockerbox}{Copia de seguridad del directorio de instancia}
docker compose down
cp -a instance "instance.backup.$(date +%Y%m%d-%H%M%S)"
docker compose up -d
\end{dockerbox}

De esta forma se conserva una copia completa del estado persistente de la aplicación, incluyendo base de datos, modelos, imágenes, colecciones y resultados.

\subsection{Variables de entorno principales}

El fichero \texttt{.env} centraliza la configuración del despliegue. Una de las variables más importantes es:

\begin{infocmdbox}{Ruta de instancia de Flask}
FLASK_INSTANCE_PATH=/app/instance
\end{infocmdbox}

Esta variable fija la ruta de instancia de Flask dentro del contenedor. Gracias a ella, la aplicación utiliza \texttt{/app/instance} como directorio persistente único, evitando depender de la ruta por defecto calculada por Flask a partir del paquete Python.

Las variables principales del servicio web son:

\begin{infocmdbox}{Variables principales del servicio web}
WEB_CONCURRENCY=1
GUNICORN_THREADS=4
HOST_PORT=8000
SESSION_COOKIE_SECURE=false
SESSION_COOKIE_SAMESITE=Lax
\end{infocmdbox}

\texttt{WEB\_CONCURRENCY=1} mantiene un único proceso Gunicorn, decisión adecuada para reducir conflictos con SQLite y evitar duplicar lógica de procesamiento. \texttt{GUNICORN\_THREADS=4} permite concurrencia HTTP ligera dentro del proceso web. \texttt{HOST\_PORT=8000} define el puerto expuesto por la aplicación y las variables de sesión controlan el comportamiento de las cookies en el entorno de despliegue.

Las variables relacionadas con el procesamiento de trazas son:

\begin{infocmdbox}{Variables de procesamiento de trazas}
AUTO_START_TRACE_WORKER=false
TRACE_WORKER_CONCURRENCY=1
TRACE_WORKER_BATCH_SIZE=1
TRACE_WORKER_STALE_SECONDS=600
\end{infocmdbox}

\texttt{AUTO\_START\_TRACE\_WORKER=false} indica que el servicio web no debe arrancar \textit{workers} internos en Docker. El procesamiento debe realizarse desde el servicio \texttt{worker}. \texttt{TRACE\_WORKER\_CONCURRENCY=1} establece el número de \textit{workers} lógicos dentro del servicio de procesamiento, manteniendo un modo conservador. \texttt{TRACE\_WORKER\_BATCH\_SIZE=1} hace que se reclamen pocas teselas por iteración, reduciendo la presión sobre SQLite y la GPU. Por último, \texttt{TRACE\_WORKER\_STALE\_SECONDS=600} permite recuperar teselas que hayan quedado atascadas en estado \texttt{processing}.

Las variables principales de inferencia y modelos son:

\begin{infocmdbox}{Variables principales de inferencia y modelos}
SEG_USE_GPU=true
MODEL_VALIDATION_USE_GPU=true
SEG_DEFAULT_ACTIVE_FOLD=fold.0
SEG_N_FOLDS=3
\end{infocmdbox}

\texttt{SEG\_USE\_GPU=true} habilita el uso de CUDA si PyTorch detecta una GPU compatible. \texttt{MODEL\_VALIDATION\_USE\_GPU=true} permite validar modelos utilizando GPU. \texttt{SEG\_DEFAULT\_ACTIVE\_FOLD=fold.0} define el modelo activo inicial y \texttt{SEG\_N\_FOLDS=3}, este último se ajustará en base al número de modelos recibidos.

\subsection{Comprobación de GPU}

En despliegues con aceleración por GPU es necesario comprobar que el servidor, Docker y PyTorch detectan correctamente el hardware disponible. En primer lugar, desde el propio servidor puede revisarse el estado de las GPU con:

\begin{dockerbox}{Comprobación de GPU en el servidor}
nvidia-smi
\end{dockerbox}

Dentro del servicio \texttt{web}, la comprobación básica de PyTorch puede realizarse con:

\begin{dockerbox}{Comprobación de PyTorch en el servicio web}
docker compose exec -T web python - <<'PY'
import torch
print(torch.__version__)
print(torch.version.cuda)
print(torch.cuda.is_available())
print(torch.cuda.device_count())
PY
\end{dockerbox}

La misma comprobación puede realizarse dentro del servicio \texttt{worker}:

\begin{dockerbox}{Comprobación de PyTorch en el servicio worker}
docker compose exec -T worker python - <<'PY'
import torch

print(torch.__version__)
print(torch.version.cuda)
print(torch.cuda.is_available())
print(torch.cuda.device_count())
PY
\end{dockerbox}

Aunque \texttt{torch.cuda.is\_available()} indique que PyTorch detecta CUDA, esto no garantiza por sí solo que los \textit{kernels} se ejecuten correctamente en la GPU. Por ello, conviene ejecutar al menos una operación real en CUDA:

\begin{dockerbox}{Prueba real de operación en CUDA}
docker compose exec -T web python - <<'PY'
import torch

x = torch.randn((1024, 1024), device="cuda")
y = x @ x
print(y.mean().item())
PY
\end{dockerbox}

Esta prueba confirma que PyTorch no solo detecta CUDA, sino que puede ejecutar operaciones reales sobre GPU. Además, \texttt{nvidia-smi} permite observar el consumo de memoria y los procesos asociados durante la ejecución. En el servidor Gamma fue necesario utilizar versiones compatibles con las GPU NVIDIA TITAN Xp, concretamente \texttt{torch 2.7.1+cu118} y \texttt{torchvision 0.22.1+cu118}, ya que otras versiones más recientes con CUDA no ofrecían soporte adecuado para su arquitectura.

\subsection{Problemas frecuentes}

Durante la instalación, ejecución local o despliegue con Docker pueden aparecer algunos problemas habituales. A continuación se recogen los más relevantes y las comprobaciones recomendadas para diagnosticarlos.

\begin{itemize}
	\item \textbf{\texttt{ModuleNotFoundError: No module named 'trazasytrazadas'.}} Este error suele indicar que las pruebas se han ejecutado desde una ubicación incorrecta o que no se está aplicando la configuración de \texttt{pytest.ini}. Debe comprobarse que se ejecuta desde la raíz del repositorio y que existe la línea \texttt{pythonpath = webapp}.
	
	\item \textbf{No se encuentra Flask o alguna dependencia.} Normalmente se debe a que el entorno virtual no está activado o a que no se han instalado las dependencias. Debe activarse el entorno y ejecutar \texttt{pip install -r webapp/requirements.txt}.
	
	\item \textbf{Docker no encuentra \texttt{docker-compose.yml}.} Este problema aparece cuando se ejecuta \texttt{docker compose} desde una carpeta que no corresponde a la raíz del proyecto. La raíz debe contener, entre otros elementos, \texttt{Dockerfile}, \texttt{docker-compose.yml}, \texttt{webapp/} y \texttt{docker/}. Para comprobar el estado de los servicios debe situarse primero en dicha carpeta:
	
	\begin{dockerboxnf}{Comprobación de servicios Docker}
cd ~/trazasytrazadas
docker compose ps
	\end{dockerboxnf}
	
	\item \textbf{Los modelos aparecen como ``sin fichero''.} Las causas más habituales son que los modelos no estén ubicados en \texttt{instance/model}, que \texttt{SEG\_MODELS\_DIR} no apunte a \texttt{/app/instance/model}, que no se haya definido \texttt{FLASK\_INSTANCE\_PATH=/app/instance}, que se haya copiado la base de datos SQLite pero no los ficheros físicos de modelo, o que \texttt{SEG\_N\_FOLDS} no coincida con los modelos entregados. Puede comprobarse la configuración real dentro del contenedor mediante:
	
	\begin{dockerboxnf}{Comprobación de rutas de modelos en el contenedor}
docker compose exec -T web python - <<'PY'
from trazasytrazadas import create_app

app = create_app()
with app.app_context():
print(app.instance_path)
print(app.config["SEG_MODELS_DIR"])
PY
	\end{dockerboxnf}
	
	El resultado esperado debe ser:
	
	\begin{infocmdboxnf}{Rutas esperadas de instancia y modelos}
/app/instance
/app/instance/model
	\end{infocmdboxnf}
	
	También debe comprobarse que los ficheros existen físicamente:
	
	\begin{dockerboxnf}{Comprobación de ficheros de modelos}
docker compose exec web ls -lh /app/instance/model
	\end{dockerboxnf}
	
	Solo se entregan tres modelos, por lo que, debe ajustarse la variable correspondiente:
	
	\begin{infocmdboxnf}{Número de modelos entregados}
SEG_N_FOLDS=3
	\end{infocmdboxnf}
	
	\item Las imágenes de perfil aparecen rotas. Este problema puede deberse a que no se ha copiado el directorio \texttt{instance/profile\_images}, a que la base de datos referencia imágenes que no existen físicamente, a permisos incorrectos sobre \texttt{instance} o a que \texttt{PROFILE\_IMAGE\_FOLDER} no apunta a \texttt{/app/instance/profile\_images}. La ruta configurada puede comprobarse con:
	
	\begin{dockerboxnf}{Comprobación de ruta de imágenes de perfil}
docker compose exec -T web python - <<'PY'
from trazasytrazadas import create_app

app = create_app()
with app.app_context():
print(app.config["PROFILE_IMAGE_FOLDER"])
PY
	\end{dockerboxnf}
	
	Y los ficheros disponibles pueden revisarse mediante:
	
	\begin{dockerboxnf}{Listado de imágenes de perfil disponibles}
docker compose exec web find /app/instance/profile_images -maxdepth 4 -type f
	\end{dockerboxnf}
	
	\item \texttt{No space left on device}. Este error suele producirse cuando se han incluido modelos dentro de la imagen Docker, cuando \texttt{.dockerignore} no excluye correctamente \texttt{instance} o cuando se copia un entorno virtual dentro de la imagen. Debe revisarse el fichero \texttt{.dockerignore}, que debería excluir, al menos:
	
	\begin{infocmdboxnf}{Entradas recomendadas en .dockerignore}
instance/
webapp/instance/
venv/
.venv/
TFG_env/
.venv-test/
__pycache__/
.pytest_cache/
htmlcov/
	\end{infocmdboxnf}
	
	Los modelos no deben copiarse dentro de la imagen, sino montarse mediante volúmenes. Para liberar espacio puede realizarse una limpieza prudente con:
	
	\begin{dockerboxnf}{Limpieza prudente de imágenes y caché Docker}
docker builder prune -af
docker image prune -af
	\end{dockerboxnf}
	
	No se recomienda utilizar como primera opción \texttt{docker system prune --volumes}, ya que puede eliminar volúmenes persistentes si se están usando para almacenar datos de la aplicación.
	
	\item No se crean ficheros en \texttt{instance}. Este problema suele estar relacionado con permisos incorrectos, con la ausencia de \texttt{FLASK\_INSTANCE\_PATH}, con que el \texttt{entrypoint.sh} no haya creado las carpetas necesarias o con que el volumen no esté montado correctamente. Debe comprobarse que las rutas internas apuntan a \texttt{/app/instance/...}:
	
	\begin{dockerboxnf}{Comprobación de rutas internas de instancia}
docker compose exec -T web python - <<'PY'
from trazasytrazadas import create_app

app = create_app()
with app.app_context():
print(app.instance_path)
print(app.config["DATABASE"])
print(app.config["UPLOAD_FOLDER"])
print(app.config["OUTPUT_FOLDER"])
PY
	\end{dockerboxnf}
	
	\item Las traducciones no aparecen actualizadas. En este caso conviene recompilar los catálogos mediante \\
	\texttt{pybabel compile -d trazasytrazadas/translations} desde el directorio \texttt{webapp}.
	
	\item Error al arrancar Gunicorn. Debe comprobarse que el comando se ejecuta desde \texttt{webapp} o que la ruta de Python incluye dicho directorio. También debe verificarse que Gunicorn tiene acceso al paquete \texttt{trazasytrazadas} y que el directorio \texttt{instance} dispone de permisos adecuados.
	
	\item La GPU no se utiliza en el despliegue. Las causas habituales son que Docker no exponga la GPU al contenedor, que NVIDIA Container Toolkit no esté configurado, que la versión de PyTorch instalada sea solo CPU, que la \textit{build} CUDA no sea compatible con la GPU o que \texttt{SEG\_USE\_GPU} esté desactivado. En el servidor puede comprobarse la disponibilidad de GPU con:
	
	\begin{dockerboxnf}{Comprobación de GPU en el servidor}
nvidia-smi
	\end{dockerboxnf}
	
	Dentro del contenedor puede verificarse PyTorch mediante:
	
	\begin{dockerboxnf}{Comprobación de CUDA y PyTorch dentro del contenedor}
docker compose exec -T web python - <<'PY'
import torch
print(torch.__version__)
print(torch.version.cuda)
print(torch.cuda.is_available())
print(torch.cuda.device_count())
PY
	\end{dockerboxnf}
	
	Además, en el fichero \texttt{.env} debe comprobarse que estén activadas las opciones correspondientes:
	
	\begin{infocmdboxnf}{Activación de GPU en el fichero .env}
SEG_USE_GPU=true
MODEL_VALIDATION_USE_GPU=true
	\end{infocmdboxnf}
	
	\item Aparecen advertencias de compatibilidad \texttt{sm\_61}. Las GPU NVIDIA TITAN Xp del servidor Gamma tienen capacidad CUDA \texttt{sm\_61}. Algunas versiones modernas de PyTorch con CUDA no incluyen soporte para esta arquitectura. En particular, \texttt{torch 2.10.0+cu128} podía detectar CUDA, pero mostraba advertencias de incompatibilidad de arquitectura, por lo que no era una configuración segura para inferencia real en ese servidor. La versión validada en Docker fue:
	
	\begin{infocmdboxnf}{Versiones validadas de PyTorch y Torchvision}
torch 2.7.1+cu118
torchvision 0.22.1+cu118
	\end{infocmdboxnf}
	
	\item El servicio web procesa colecciones aunque existe un servicio \textit{worker}. Este comportamiento suele indicar que \texttt{AUTO\_START\_TRACE\_WORKER=true} está configurado en el servicio web. En un despliegue Docker de producción, el servicio \texttt{web} no debe arrancar automáticamente el procesamiento de trazas. La configuración esperada es:
	
	\begin{infocmdboxnf}{Configuración esperada del worker}
AUTO_START_TRACE_WORKER=false
	\end{infocmdboxnf}
	
	El procesamiento debe quedar delegado al servicio \texttt{worker} definido en Docker Compose.
\end{itemize}

\section{Pruebas del sistema}

En esta sección se recogen las pruebas funcionales realizadas sobre la aplicación mediante casos de prueba derivados de los principales flujos de usuario. Estas pruebas se han validado sobre la versión final de la \textit{suite} Selenium, por lo que todos los casos descritos presentan estado de ejecución satisfactorio. El objetivo de este apartado es documentar, de forma estructurada, qué funcionalidad se comprueba en cada caso, qué condiciones deben cumplirse antes de ejecutarlo y qué resultado se obtiene tras cada paso.

\subsection{Pruebas con Selenium}

Para la validación funcional de la aplicación se ha utilizado \textit{Selenium WebDriver} integrado con \texttt{pytest}. No se ha empleado Selenium IDE como herramienta principal, sino una suite automatizada de pruebas de navegador ubicada en el directorio \texttt{tests/selenium}. Estas pruebas se ejecutan desde la raíz del repositorio, donde se encuentra el fichero \texttt{pytest.ini}, encargado de registrar el marcador \texttt{selenium} y de añadir \texttt{webapp} al \texttt{pythonpath}, permitiendo localizar correctamente la aplicación Flask.

La suite utiliza \textit{fixtures} de \texttt{pytest} para preparar el entorno de prueba: arranca la aplicación en un servidor aislado, inicializa una base de datos independiente, lanza el navegador mediante Selenium Manager y limpia los recursos generados tras la ejecución. Gracias a Selenium Manager, en condiciones normales no es necesario descargar manualmente \texttt{ChromeDriver}, ya que el propio entorno resuelve el controlador adecuado para el navegador.

Las pruebas Selenium pueden ejecutarse con el navegador en segundo plano mediante el siguiente comando:

\begin{testbox}{Ejecución de pruebas Selenium en segundo plano}
pytest tests/selenium --selenium -q
\end{testbox}

Si se desea visualizar la ejecución en el navegador, puede añadirse la opción \texttt{--selenium-headed}:

\begin{testbox}{Ejecución de pruebas Selenium con navegador visible}
pytest tests/selenium --selenium --selenium-headed -q
\end{testbox}

También existe la posibilidad de ralentizar la ejecución para facilitar la inspección visual de los pasos, por ejemplo:

\begin{testbox}{Ejecución de pruebas Selenium ralentizada}
pytest tests/selenium --selenium --selenium-headed --selenium-slow-ms=350 -q
\end{testbox}
